# Preferences

Source: `tests/Preferences.spec.ts` — **18 cases**, collected in `test-group5`.

## Setup and boundaries

Each case opens a fresh page, resets preferences, and loads the deterministic 16×16 `cube.fits`. Other cases reuse `single.fits`, `matching-cube.fits`, `iquv.fits`, `flux-beam.fits`, and the small catalog fixtures. No additional image data is needed. Viewer screenshots wait for the temporary image-size indicator to fade out before comparison.

The spec supplies a separate in-memory `/database/preferences` endpoint for each page, recording PUT updates and DELETE keys and returning them on subsequent GETs. This checks dialog-to-API wiring and reload behavior without parallel tests overwriting saved preferences. It does **not** establish persistence on the real database server. FITS loading, profiles, regions, contours, vector generation, and catalog loading still use the configured CARTA backend. Telemetry token and submission requests are mocked locally; clipboard access is tested with a deterministic anonymous ID.

All tabs exercise their controls through the UI, assert preference state and save requests, and restore their initial controls. Reset checks verify that the selected tab's keys are deleted while unrelated telemetry settings remain. After each case, including failures, teardown resets all preferences and checks that only the disabled-telemetry settings and anonymous telemetry UUID remain. The shared reset helper deliberately preserves this UUID. PNGs cover the viewer in each workflow; image-affecting settings also check consumer state and RGB values. Numeric inputs exercise increment/decrement buttons as well as text entry.

## Related coverage

- `Layout.spec.ts` / [Layout plan](./Layout.md): dynamic data-type mappings, mapping editing/removal, and real saved-layout lifecycle. The Preferences spec adds startup-layout and higher-dimension-priority controls rather than duplicating mapping workflows.
- `PVImage.spec.ts` / [PV plan](./PVImage.md): the minimum saved memory limit is exercised with actual rebin and cropped-region previews. The Preferences spec covers the control, units, and reset.
- Widget specs continue to own detailed per-widget rendering, editing, and matching behavior. Frontend unit tests own scaling math, colormap helpers, catalog column-selection permutations, and workspace configuration serialization; these E2E cases check visible preference wiring and representative consumers.

Run with `npm test -- --project=test-group5 Preferences --workers=2 --retries=0`. Baseline images are under `tests/Preferences.spec.ts-snapshots/`; review them when the configured frontend or platform changes. Case counts describe collection, not passing results.
